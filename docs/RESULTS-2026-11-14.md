## Data-dependent outcomes observed

- UI-022 (borrowed RGB channel): a frame with a borrowed channel (marked `*`)
  was found within the scanned frames and "This frame" showed the source
  `(from <date>)`, on both projects.
- UI-029 (saturation flags): flagged frames found; the card showed UTC date,
  detectors, exposures, coverage and flag chips.
- UI-020 note: with `det=5,6` the frame chips showed only the detector that
  actually observed the target that day (`D6` for the sampled frame) — the
  suite asserts no foreign detector rather than both chips, per features.md §5.

## During-development findings (not part of the authoritative run)

Recorded for honesty, they shaped the suite:

- The hosting platform served a **502 error page / restart window** during the
  first desktop run (UI-005, UI-006, UI-007, UI-013, UI-017 failed on
  navigation, not on behaviour). The suite now waits such windows out in
  `open()`; the viewer itself ships a "Updating the site, back in a moment…"
  note for them.
- One transient UI-034 failure on the smartphone project in an intermediate
  run (hintbox not shown after the first Tab); the behaviour reproduced green
  3/3 in a probe and passed in the authoritative run. The wait window was
  widened to absorb slow first loads.
- Oracle corrections after reading the live v21 client: "All bands"/`det=5,6`
  chips list only the detectors that observed the day; the map zoom keeps the
  sky point under the pointer, so an exact-pixel return after zoom-out is not
  part of the behaviour; the search box is pre-filled with the target name.

## Not covered by automation

- Scientific correctness of images, photometry, spectra (data-level testing).
- Real-device touch/pinch/rotation (UI-038), screen-reader walkthrough (UI-035
  covers reduced motion only), network-loss recovery (UI-036).
- Fetching the GIF/data share endpoints (UI-032 checks links only, to avoid
  starting render jobs on the shared server).
